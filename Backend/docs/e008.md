# E0-08: cola de aprobacion de dos personas

Implementacion de [E0-08 #349](https://github.com/hugo-chicaiza/Banking-Platform/issues/349). Se conserva E0-09 integrado en develop. E0-10 y E1-10 deben registrar sus operaciones sobre esta cola, sin crear otra cola ni ejecutar un cambio sensible antes de aprobarlo.

## Flujo y seguridad

`POST /api/v1/aprobaciones` valida la operacion registrada y su objetivo, congela cambio, antes, despues y version, persiste la solicitud y devuelve **202** con `idSolicitud`, `estado: Pendiente` y `requiereAprobacion: true`. No modifica el objetivo. El cliente compartido del frontend comprueba ese estado HTTP y valida la respuesta con Zod.

El registro de manejadores es explicito. Un codigo no registrado no ejecuta contenido recibido del cliente. Se valida el catalogo SQL de operaciones; ese catalogo no concede identidades ni sustituye WorkOS. El adaptador real inicial es `PAR-EDITAR`, para parametros sensibles de E0-09. El adaptador de agencias corresponde a E0-10.

Cada peticion revalida la membresia activa, los roles y los permisos efectivos de WorkOS, la organizacion configurada, el vinculo institucional activo y las agencias asignadas. ADMIN no recibe aprobacion automaticamente. Los permisos autorizados son `parametros:aprobar` y `agencias:aprobar`; la distribucion inicial de desarrollo es SUPERVISOR. El solicitante nunca aprueba su solicitud. Cambiar el permiso en el navegador no concede acceso.

La autorizacion de la operacion y el contexto de agencia se comprueban en backend. Un recurso fuera del alcance devuelve 404. Las escrituras respetan la agencia operativa y la proteccion de contexto entre pestanas de #450. Una consulta visible o una opcion de menu nunca sustituye estos controles.

Los estados son Pendiente, Aprobada, Ejecutada, Rechazada, Cancelada y Fallida. No existe vencimiento por antiguedad. Rechazar exige comentario. La cancelacion de usuario solo corresponde al solicitante y a una solicitud Pendiente.

## Transacciones, concurrencia y recuperacion

- En SeguridadDB, aprobar, aplicar y registrar Ejecutada comparten una transaccion. Un fallo revierte todo y conserva Pendiente.
- En CooperativaDB, primero se confirma Aprobada en SeguridadDB. El cambio, comprobante y evento pendiente se confirman juntos en la base destino. Despues se confirma Ejecutada en SeguridadDB.
- Un bloqueo de aplicacion por organizacion/solicitud y el comprobante unico impiden repetir el efecto. Dos aprobadores compiten por la misma fila; el segundo recibe 409 `SOLICITUD_NO_PENDIENTE`.
- La version del objetivo se revalida bajo bloqueo. Si cambio, se devuelve 409 `SOLICITUD_DESACTUALIZADA` sin aplicar la propuesta.
- Un fallo transitorio deja Aprobada y devuelve 503 `APROBACION_PENDIENTE_RECUPERACION`. No se debe crear otra solicitud. La tarea termina usando el comprobante existente o aplica una sola vez. Un rechazo permanente del objetivo deja Fallida.
- La perdida de permisos o desactivacion del solicitante cancela solicitudes pendientes. Una indisponibilidad de WorkOS no se interpreta como revocacion. Las operaciones aun no registradas no se cancelan por ese motivo.

El relevo lleva los eventos a la bitacora institucional, con deduplicacion por UUID y detalle inmutable. La auditoria conserva solicitante, aprobador, roles, agencia, fecha UTC, origen, correlacion y antes/despues. No contiene cookies ni tokens. El trigger autorizado de Auditoria.Auditoria protege UPDATE solo de las filas nuevas vinculadas al detalle E0-08; los INSERT y las filas anteriores mantienen su comportamiento.

## Tareas operativas

Las tareas registradas son `APR_RECUPERACION`, `APR_RESUMEN_ANTIGUAS` y `APR_AUD_RELEVO`. El ciclo se ejecuta cada 60 segundos durante la vida de FastAPI; el resumen es diario. Cada tarea tiene exclusion SQL entre instancias y registro persistido de resultado. La antiguedad se obtiene de `APR_DIAS_RESALTAR`, sin cerrar solicitudes.

Tambien se pueden ejecutar con `python -m app.modules.aprobaciones.tareas CODIGO`, usando la configuracion segura del entorno correcto. No ejecutar una instancia contra otra organizacion ni instalar credenciales dentro del repositorio. El arranque no ejecuta migraciones.

No retirar el trigger protector mientras existan eventos vinculados. Cualquier retiro de objetos compartidos necesita revision y autorizacion; no se incluye un down destructivo.

## Frontend

Rutas `/aprobaciones` y `/aprobaciones/:idSolicitud`, dentro del layout existente. Menu de primer nivel con contador confirmado por la API; pestanas Pendientes para mi, Mis solicitudes y Resueltas; paginacion; antiguedad resaltada; comparacion; historial con responsable y su ID; confirmaciones y errores con correlacion.

Se reutilizan React Query, Zod, cliente HTTP y componentes del proyecto. Los componentes nuevos reutilizables son ComparadorCambios, LineaDeTiempo, AvisoRequiereAprobacion y ErrorApi. Una respuesta Aprobada no se presenta como Ejecutada.

La navegacion conserva los accesos unificados de develop. Aprobaciones se autoriza por operacion y propiedad mediante `/aprobaciones/accesos`; no se agrega al catalogo de secciones configurables. Personalizar un menu no concede permisos de aprobacion. Un usuario que pierde el permiso puede seguir consultando sus propias solicitudes e historial.

## Matriz de trazabilidad

| AC original | Implementacion | Evidencia | Estado |
|---|---|---|---|
| 1. 202, Pendiente persistida, objetivo intacto | router, servicio, manejadores | SQL local y HTTP; cliente frontend real con WorkOS y verificacion Azure antes de aprobar | APROBADO |
| 2. Propia: 403 APROBADOR_ES_SOLICITANTE e intento auditado | servicio, auditoria, relevo | SQL local y peticion real desde navegador | APROBADO |
| 3. Otro aprobador con alcance, ejecucion y dos identidades en auditoria | identidad, servicio, lecturas, relevo | Aprobacion desde pantalla; persistencia y auditoria Azure con dos identidades reales; negativo de agencia | APROBADO |
| 4. Dos aprobadores: un exito y un 409 | repositorio, servicio, indice de solicitud activa | Carrera SQL local y carrera real desde dos sesiones WorkOS distintas | APROBADO |
| 5. Objetivo cambiado: 409 y nada aplicado | manejadores, servicio | Cambio solo de parametro QA propio; API real devuelve SOLICITUD_DESACTUALIZADA; valor intacto y error visible | APROBADO |
| 6. No vence por tiempo | tareas, servicio, lecturas | SQL local; fixture propia Azure con antiguedad simulada de 730 dias, resaltada y aprobada desde pantalla | APROBADO |
| 7. Recuperacion entre bases sin efecto duplicado | servicio, tareas, comprobante, relevo | Fallos SQL locales y fallo controlado privado despues del commit Azure: 503, recuperacion real, un comprobante y un valor | APROBADO |
| 8. Alteracion detectada por hash | congelacion, servicio, trigger | SQL local propio con inyeccion de corrupcion y rechazo de aprobacion; Azure impide modificar el hash y protege auditoria | APROBADO |

La antiguedad de 730 dias es una fixture tecnica explicita, no una solicitud humana realmente creada hace dos anos. Sus eventos se registraron con fecha real y autor de sistema. La inyeccion de corrupcion requirio deshabilitar un trigger exclusivamente en una base SQL local propia; nunca se deshabilitaron triggers compartidos. La inyeccion del fallo entre bases fue temporal, para un ID QA propio y fuera del repositorio.
